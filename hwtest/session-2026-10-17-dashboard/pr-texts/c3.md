Follow-up: phase between consecutive I/Q waterfall frames, tested on hardware on both boards (new `hwtest/rf_iq_frame_phase_check.py`, README and changelog updated).

The I/Q waterfall holds the last FFT frame of each integration, so consecutive frames should be exactly `number_integrations * 4096` samples apart. A single tone cannot show that (the references drift by tens of Hz over the 68 to 100 ms between frames), so the check sends two tones from one TX buffer, 8.356 bins apart, and follows the phase of X1 * conj(X2) at the two peak bins. It rotates at the difference frequency as the receiver sees it (TX difference scaled by the sample clock ratio, taken from the carrier offset), so the prediction is `2 pi (f1 - f2) (1 + delta) nint 4096 / fs`. A lost frame or a spacing off by one FFT frame would change it (by 2.2 rad for the latter).

Result, 101 frames per run (148 at 61.44 MS/s), nint set for ~100 ms between frames (1023 at 61.44) and restored afterwards: measured minus predicted rotation per frame is within 0.0035 rad on both boards at 2.5, 10, 20, 30.72 and 61.44 MS/s (Pluto -0.0018 to 0.0004, Pluto+ 0.0001 to 0.0035 rad), scatter 0.001 to 0.002 rad, and no frame deviates by more than 0.3 rad. So the I/Q frames are phase coherent and exactly nint * 4096 samples apart, with no lost frame (one websocket arrival gap of 143 ms for a 100 ms period at 20 MS/s on the Pluto+, with no phase jump).

Single-tone phase between I/Q frames is not predictable on this rig (second difference 0.25 to 0.6 rad rms, the board reference drift), so it was not checked; absolute level (dBm) is still untested.
