## rf_iq_check: the I/Q peak may sit on a neighbouring bin (commit cffbb45)

While testing a firmware image with the new dashboard, one run of `rf_iq_check.py` on the Pluto+ (2.5 MS/s, cw -600 kHz) reported FAIL. The check required the per-frame I/Q peak to be exactly the magnitude peak bin.

Re-running that check alone 14 times gave 13 ok and 1 FAIL. In the second FAIL the I/Q peak split over bins 985 and 986 (magnitude peak 985, raw capture correlation 1.0). The carrier offset between the boards drifts (measured -48.4 kHz), which puts this tone at bin position 985.59 to 985.68, near the half-bin boundary, so the peak of a single frame can land on either neighbour. The raw, magnitude and I/Q peaks agree within one bin in every run, so I read this as a criterion that is too strict, not a data error.

The check now accepts every I/Q peak within one bin of the magnitude peak (two bins away still fails). The README line for the check mentions it. Checked on hardware: two runs on the Pluto+ at 2.5 MS/s, all CW tones and the OFDM test ok.

Not changed: the 0.99 threshold for the raw capture against the magnitude waterfall correlation. The first FAIL also had a correlation of 0.961 (with I/Q peaks on bins 984 and 985), and I could not show that the split peak explains it, so I left that threshold alone. I did not run pycodestyle (not installed on my machine).
